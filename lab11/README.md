## 📄 Формат входного файла `todos.json`

Файл должен быть сохранён в кодировке **UTF-8** и содержать JSON-массив объектов, где у каждой записи присутствуют:

* `id` — уникальное положительное целое число (`type(x) is int`);
* `userId` — положительное целое число (`type(x) is int`);
* `title` — непустая строка (`str`);
* `completed` — логическое значение (`type(x) is bool`).

Содержимое `todos.json`:

```json
[
  {"id": 1, "userId": 5, "title": "Ввод", "completed": true},
  {"id": 2, "userId": 5, "title": "Циклы", "completed": false},
  {"id": 3, "userId": 10, "title": "Строки", "completed": true},
  {"id": 4, "userId": 10, "title": "Файлы", "completed": true},
  {"id": 5, "userId": 5, "title": "Списки", "completed": true}
]
```

## 🌐 Пояснения по HTTP (Сетевое упражнение)

* **Адрес запроса:** `https://api.github.com/users/<login>` обращается к ресурсу профиля конкретного пользователя GitHub (а не репозитория, для которого нужен путь с владельцем и именем репозитория).
* **Метод GET:** запрашивает данные ресурса без изменения состояния на сервере (`200` — успех, `404` — профиль не найден, `403` / `429` — ограничения доступа или частоты запросов).
* **Таймаут (`timeout=10`):** ограничивает ожидание ответа сети, чтобы запрос не зависал при проблемах со связью.
* **Заголовки (`Accept`, `User-Agent`):** задают ожидаемый формат ответа JSON и идентифицируют клиент при обращении к API GitHub.
* **Обработка ошибок:** отдельно перехватываются `HTTPError` (коды ответа сервера), сетевые и таймаут-ошибки (`URLError`, `TimeoutError`, `socket.timeout`), ошибки данных/кодировки (`ValueError`, `UnicodeError`) и файлового доступа (`OSError`). При отсутствии сети используется локальный `profile_sample.json` с полями `login`, `id`, `name: null` без подмены `null` выдуманными значениями.

## ⚙️ Ответы на вопросы из раздела «Проверки и сдача»

* **Почему в тесте учебного набора проверяются количества, лидеры и идентификаторы выборки?** Это гарантирует, что все ключевые этапы обработки (`completion_counts`, `top_users`, `select_tasks`) согласованы между собой и дают точный результат на эталонном наборе данных.
* **Как ведут себя функции на пустом списке и наборе, где все задачи имеют `completed=false`?** При пустом списке или нулевом максимуме завершённых задач `top_users` возвращает `[]`, а выборка задач оказывается пустой (`[]`), без падения на поиске максимума.
* **Зачем проверять отдельно один лидер и несколько лидеров с одинаковым результатом?** Это подтверждает, что функция корректно отбирает всех участников с максимальным значением, а не останавливается на первом найденном или не возвращает лишних при ничьей.
* **Зачем проверять неизвестного пользователя и набор без совпадений по варианту?** В обоих случаях результат должен быть пустым списком `[]`, что показывает корректную фильтрацию без выхода за границы списка и без ошибок по ключам.
* **Почему при проверке валидации тестируются не список в корне, повторный `id`, отсутствующий `userId`, `completed="false"` и `id=true`?** Эти кейсы закрывают главные ловушки формата и типов: неверную корневую структуру, дубликаты идентификаторов, пропущенные обязательные поля, строковое `"false"` вместо логического значения и `bool` (`True`/`False`), который в Python является подклассом `int`.
* **Зачем проверять равенство структуры после записи и повторного чтения JSON?** Проверка подтверждает, что при сериализации и десериализации не теряются поля, типы и порядок записей, а исходные словари при этом не мутируют.
* **Почему сетевые вызовы не должны выполняться при импорте модулей тестами?** Если сетевой запрос лежит на верхнем уровне модуля без защиты `if __name__ == "__main__":` или вызова внутри функции, импорт в тестах пойдёт в сеть, замедлит прогон и сделает тесты зависимыми от интернета.
